Lifecycle

run() loads fragments, applies bindings, and attaches event and form handlers before notifying listeners that rendering is complete.

Render order#

BitsyJS runs these steps in order, so fragments and scopes are in place before directives run.

  1. Fragments load. Every b-view is fetched, nested fragments are resolved relative to their parent fragment, and the results are inlined. This step is awaited.
  2. Data scopes attach. Each b-data attribute is parsed as a JavaScript object literal, stored as a scope, and its subtree is bound. Attribute and text placeholders render here.
  3. Directives run. b-for first, then b-if, then b-js. A loop resolves b-if, b-js and b-on inside each row while it builds that row.
  4. Containers unwrap. Every <b-container> is replaced by its own children.
  5. Scope attributes are removed. The b-data attributes are stripped from the page.
  6. Events attach. data-b-event listeners and b-on:* listeners are attached, and the b-on:* attributes are removed. The data-b-event attribute names the event only when the listener is attached, but the data-b-event-* modifiers are read again on every event, so they stay on the element.
  7. Forms wire up. Submit listeners are attached to forms marked with data-b-validate-form="true" or data-b-form-ajax="true".
  8. The rendered bus event dispatches. Event.dispatch("bitsy.rendered") runs every callback registered with on("rendered") or ready(), in registration order.
  9. The DOM event dispatches. window.__bitsyRendered is set to true, then a CustomEvent named bitsy:rendered is dispatched on document.
  10. run() resolves. The promise settles after the DOM event, not before it.

By the time rendered listeners run, loop and fragment content is in the document and its handlers are attached.

Async behaviour#

run() awaits the fragment step even if there are no fragments. The remaining render steps and event dispatches run synchronously, but BitsyJS does not await promises returned by listeners.

  • Use await bitsy.run() before reading the initial rendered DOM. Signal updates can still change it later.
  • Without await, code after the call can run before bindings are applied, even on a page with no b-view.
  • Bindings that read a signal are live afterwards. They are effects created during the render, not a second pass over the page.
  • Calling run() twice on one instance is not supported. Use a new instance for markup that was not part of the first run, and remember that the new instance scans the whole document. 
const bitsy = new BitsyJS({ data: { title: "Status" } });

// Not awaited: the fragment step yields before anything is bound.
const pending = bitsy.run();

// Awaited: the DOM is rendered, events are attached, listeners have run.
await pending;

The rendered event#

Rendering ends with two dispatches. The first is the library's own event bus, the second is a DOM event. Both are synchronous and both happen before run() resolves.

Where the rendered notification is dispatched and how to listen for it
Target Name How to listen
Library event bus bitsy.rendered bitsy.on("rendered", cb) or bitsy.ready(cb)
Window flag window.__bitsyRendered Read it in a DOM listener, or poll it
Document bitsy:rendered document.addEventListener("bitsy:rendered", cb)

on(name, callback) prefixes the name with bitsy., so on("rendered", cb) listens to bitsy.rendered. The callback receives the argument passed to the dispatch; the rendered dispatch passes none, so it receives undefined.

Use the DOM event when you do not have the BitsyJS instance. The window flag is already true when the event fires. The pre-rendering CLI uses both. 

import { BitsyJS } from "./bitsy.min.js";

const bitsy = new BitsyJS({ data: { title: "Status" } });

bitsy.on("rendered", () => console.log("bus listener"));
document.addEventListener("bitsy:rendered", () => console.log("DOM listener", window.__bitsyRendered));

await bitsy.run();
// Logs: bus listener, then DOM listener true.

on(), ready() and late listeners#

on(name, callback) registers a listener and returns this, so calls can be chained. ready(callback) is a thin alias for on("rendered", callback) and returns nothing.

  • Listeners registered before run() fire at the end of that run.
  • Listeners registered after a render do not fire retroactively. They wait for another dispatch on the shared bus.
  • Callbacks run in registration order, synchronously, inside run().
  • A synchronous exception in a bus callback rejects run(), skipping the remaining bus callbacks and the DOM event.

Register the callback before calling run() when you need to act on that render. Do not register it after the await and expect it to fire.

The shared event bus#

All instances from the same BitsyJS module share one listener list. One instance's render can invoke another instance's ready() callback. The DOM event is also document-wide. To wait for a specific instance, await its run() promise. 

import { BitsyJS } from "./bitsy.min.js";

const defaults = new BitsyJS({ data: { label: "default" } });
const custom = new BitsyJS({ tags: { on: "x-on" } });

defaults.ready(() => console.log("default render listener"));
custom.ready(() => console.log("renamed render listener"));

await defaults.run(); // logs both listeners
await custom.run(); // logs both listeners again

See Custom tags for a page that runs two instances with different vocabularies.

    Pre-rendering#

    The package ships a Playwright-based CLI that serves a directory, opens each page, and writes the resulting HTML to disk. It is useful when crawlers or the first paint should see the rendered markup instead of placeholders. 

    npx bitsy-prerender --src=./site --dist=./dist --entry=index.html,docs/reference/lifecycle.html --timeout=15000 --clean
    Pre-render command line flags
    Flag Meaning
    --src=<dir> Source directory. Required. Served over a local HTTP server, rooted at the working directory when the source sits inside it, so relative module imports still resolve.
    --dist=<dir> Output directory. Required. The source and output directories cannot be the same or contain one another.
    --entry=a.html,b.html Comma-separated HTML files relative to the source directory. When omitted, every full document (a file that contains an <html> tag) is rendered.
    --timeout=<ms> Navigation and ready-signal timeout per page. Default 10000.
    --clean Replaces existing output after all pages render and assets are copied. Refuses the working directory and its ancestors.
    --help Prints usage and exits.

    To wait for BitsyJS before capturing a page, put this tag in its <head>:

    <meta name="bitsy-prerender" content="wait">

    After the network becomes idle, opted-in pages wait for window.__bitsyRendered or the bitsy:rendered event. Pages without the tag are captured without waiting for BitsyJS. The CLI writes the doctype, if present, and document.documentElement.outerHTML, then reports browser errors as warnings.

    A readiness timeout aborts the command. The first render is enough to signal readiness, so later renders may not be in the snapshot. Non-HTML assets are copied unchanged. HTML files that are not selected for rendering are not copied.

    To use the CLI, install playwright and its Chromium browser:

    npm install -D playwright
npx playwright install chromium

    Error behaviour#

    Some failures reject run() and stop the remaining steps. Others let rendering continue with fallback output.

    • A fragment request fails at the network level. The fetch error is logged and the flow rejects, because the fragment tree cannot be built from missing content. Nothing after the fragment step runs.
    • A fragment returns an HTTP error status. Response status: 404 is logged and the response body is still inlined.
    • b-data cannot be parsed. The literal is evaluated with new Function, and a syntax error becomes a SyntaxError that rejects run() before any binding.
    • A directive expression fails to compile or throws. b-if and b-js log a syntax or runtime error. Placeholders and b-for fall back silently. A failed placeholder displays false, b-if hides the element, b-js displays false, and b-for renders no rows.
    • A rendered bus callback throws synchronously. run() rejects, skips later bus callbacks, and does not set the ready flag or dispatch bitsy:rendered for that run.

    Remote requests and AJAX forms run after the render, so their failures never reject run(). They surface in the console instead; details are on the API reference page.
